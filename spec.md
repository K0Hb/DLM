# DLM (Dental Lab Manager) — спецификация MVP

Документ для агентной / LLM-разработки. Требования императивны: «должен», «запрещено». При конфликте с идеями из `ZTLHelp.pdf` приоритет у этого файла. DLM — упрощённая **веб**-версия учёта зуботехнической лаборатории, не копия ZTL.

Продуктовый контракт MVP (P0–P6) и post-MVP **P7** (факты оплаты). Пофазный план — [`docs/AGENT_PLAN.md`](docs/AGENT_PLAN.md). Процесс изменений при разработке — OpenSpec (`openspec/`).

---

## 1. Цель и мотивация

### Цель продукта

Веб-приложение для управления зуботехнической лабораторией: приём заказ-нарядов, назначение исполнителей на услуги, учёт выполнения, оплата труда техников, отслеживание статусов нарядов, простая фиксация оплаты заказчиком, публичный просмотр наряда по QR/ссылке.

### Фокус MVP

Акцент на **фиксации труда техников и их оплате**. Учёт выручки, баланса заказчиков и полноценный биллинг — вне MVP.

### Мотивация

Заменить/упростить сценарии десктопной ЗТЛ (`ZTLHelp.pdf`) в вебе: доступ из LAN и через интернет, без привязки только к одному рабочему столу.

### Пользователи системы

Только **сотрудники лаборатории** (с учётными записями и ролями). Внешние заказчики (клиники) **не** входят в систему. Допускается **публичный** просмотр наряда без логина по секретной ссылке/QR.

### Основной оператор

Основной дневной сценарий UI — роль **admin**: создание и ведение нарядов, справочники, статусы, доставка, отчёты. `employee` работает через личный кабинет своих услуг. `superadmin` — админ + управление пользователями.

## 2. Вне скоупа v1

Запрещено реализовывать в MVP (можно заложить расширение позже, но не строить UI/логику сейчас):

- сущность «работы» (биллинг заказчику) и прайс для клиник;
- баланс заказчика, модуль платежей с распределением по нарядам, касса, банк, возвраты, несколько платежей на одну строку/наряд;
- склад материалов, приход/расход, списание при закрытии;
- категории техников (1/2/3) как в ZTL;
- откат **из** статуса `closed` (закрытый наряд назад не возвращать);
- полноценная печать PDF (счёт, акт) как обязательная функция — приоритет у живой ссылки/QR; **допускается** браузерная печать карточки наряда / публичной страницы (`window.print`);
- мобильное приложение;
- вход/кабинет внешнего заказчика или врача;
- мультитенантность (несколько независимых лабораторий в одном инстансе);
- отзыв / перевыпуск публичного токена QR;
- полная копия exocad DentalDB (CAD-материалы, milling, implant libraries, scan modes);
- смена исполнителя после выхода строки из `assigned` (post-MVP).

## 3. Роли и права

Роли: `superadmin`, `admin`, `employee`. Один пользователь — одна роль.

| Действие | superadmin | admin | employee |
|---|---|---|---|
| Управление пользователями и ролями | да | сотрудники | нет |
| Справочники: заказчики, врачи, пациенты, услуги | да | да | нет |
| Привязка пула услуг к сотруднику | да | да | нет |
| Создание и редактирование нарядов | да | да | нет |
| Назначение исполнителя на услугу в наряде | да | да | нет |
| Смена статусов наряда (вперёд и откат по §5) | да | да | нет |
| Фиксация оплаты заказчиком (наряд целиком; один или пачка по заказчику) | да | да | нет |
| Отметить «выплачено» исполнителю по строке услуги | да | да | да (только свои) |
| Снять «выплачено» исполнителю (с лимитом 30 дней; override у superadmin) | да | да | да (только свои) |
| Взять свою услугу в работу / отметить выполненной | да | да | да (только свои) |
| Просмотр чужих нарядов / полный список | да | да | нет (только свои назначения) |
| Отчёты лаборатории: наряды, начисления, долги, воронка, по заказчикам, по услугам | да | да | нет |
| Отчёты / фильтры по **своим** услугам и выплатам | да | да | да |
| Журнал фактов оплаты (свои события) | да | да | да |
| Журнал фактов оплаты (все) | да | да | нет |
| Личный кабинет (свои услуги) | да | да | да |
| Публичная страница по QR | без логина, только чтение | | |

Дополнительно для `superadmin`: полный доступ ко всем действиям админа.

Запрещено: сотрудник создаёт или редактирует наряды, назначает исполнителей, закрывает наряды, правит справочники, видит **лабораторные** денежные отчёты (все исполнители / все заказчики). Свои выплаты и свой журнал — разрешены (P7, §5.4, §7.7).

Первый пользователь `superadmin` создаётся через `db:seed` (email/пароль из seed или ENV). Других bootstrap-сценариев в MVP нет.

## 4. Сущности и поля

Имена сущностей в коде предпочтительно на английском; в UI — на русском.

### 4.1. User (сотрудник)

- `id`
- `email` — уникальный логин (Devise)
- Devise-поля пароля (`encrypted_password` и т.д.)
- `full_name` — обязательно
- `role` — `superadmin` | `admin` | `employee`
- `active` — boolean (уволен/отключён → вход запрещён)
- `created_at`, `updated_at`

Связь: `has_and_belongs_to_many :services` — **пул услуг**, которые сотрудник может выполнять (задаёт admin/superadmin на карточке `/users/:id`).

### 4.2. Customer (заказчик)

- `id`, `name` (обязательно)
- `phone`, `email`, `address`, `notes` — опционально
- `active` — boolean
- timestamps

### 4.3. Doctor (врач)

- `id`, `full_name` (обязательно)
- `customer_id` — опционально (врач может быть привязан к заказчику/клинике; фильтровать список врачей по заказчику наряда **не** обязательно)
- `phone`, `notes` — опционально
- `active`, timestamps
- Связи: `has_many :patients`; наряды — по `work_orders.doctor_id` и через пациентов

### 4.4. Patient (пациент)

- `id`, `full_name` (обязательно)
- `doctor_id` — **обязательно** (пациент без врача не допускается)
- `notes` — опционально
- timestamps

Дубликаты ФИО допустимы. Быстрый поиск по ФИО обязателен. Заказчик пациента виден через врача (`doctor.customer`), если врач привязан к клинике.

### 4.5. Service (услуга)

Справочник того, что делает техник. **Не** прайс для заказчика.

- `id`, `name` (обязательно, уникально)
- `description` — опционально
- `technician_price` — decimal, ставка оплаты технику за **одну** единицу услуги (≥ 0)
- `active` — boolean
- timestamps

### 4.6. WorkOrder (заказ-наряд)

Правило домена: наряд относится к **не более чем одному** пациенту. Обязателен только **заказчик**; пациент и врач на наряде **опциональны** (сценарий «заказчик без клиники/пациента», например изготовление модели).

- `id`
- `number` — отображаемый номер: уникальный последовательный integer (автоинкремент отображаемого номера); схема `YYYY-NNNN` **не** используется
- `status` — см. §5
- `customer_id` — обязательно
- `doctor_id` — опционально
- `patient_id` — опционально
- `due_at` — срок сдачи / примерки (datetime), опционально, рекомендуется
- `opened_at` / `created_at` — дата создания
- `closed_at` — дата закрытия (nullable)
- `sent_at` — дата отметки «отправлен» (nullable)
- `notes` — описание наряда (UI-подпись «Описание»), опционально
- `dental_formula` — JSONB odontogram (§4.9); типы и материалы зубов из `config/odontogram.yml`
- `tooth_color` — дублирует/синхронизируется с `dental_formula.shade` (код из `config/odontogram.yml` → `shades`)
- `material_note` — опциональная общая заметка; материал по зубам — коды из конфига в `teeth[].material`
- `public_token` — уникальная криптостойкая случайная строка для публичной ссылки; создаётся при создании наряда; **не** перевыпускается
- **Оплата заказчиком (факт, не касса/банк):**
  - `customer_payment_amount` — decimal ≥ 0; **сумма к оплате** заказчиком по наряду (задаёт admin/superadmin в форме редактирования наряда); **не** равна сумме строк услуг технику; в списках и карточках показывается для неоплаченных нарядов
  - `customer_paid_amount` — decimal ≥ 0; **0 = не оплачен**, `> 0` = оплачен (факт; сумму **не** скрывать в UI)
  - `customer_paid_at` — datetime, nullable
  - `customer_paid_by_id` — User, кто зафиксировал факт (nullable до первой оплаты; заполняется при подтверждении §6.9)
- `created_by_id` — User
- timestamps

В наряде допускается **0..N** строк услуг (лимита нет). Пустой список услуг допустим в `draft`; перевод в `ready`/`closed` при наличии строк требует все `completed`; наряд без строк услуг нельзя считать «готовым к сдаче» через `ready`/`closed` (нет незавершённых строк — условие «все completed» выполняется вакуумно; **решение MVP:** наряд без строк услуг **запрещено** переводить в `ready` / `sent` / `closed` — должен быть ≥ 1 строка услуги).

Правило оплаты заказчиком (P0–P6 и P7):
- частичная оплата наряда **запрещена**: либо не оплачен (`customer_paid_amount = 0`, `paid_at` пусто), либо оплачен целиком (`customer_paid_amount > 0` + дата);
- **сумма к оплате** (`customer_payment_amount`) задаётся вручную на наряде; автоподстановка из суммы строк услуг технику **запрещена**;
- факт «оплачен / не оплачен» — через страницу подтверждения (§6.9); на подтверждении сумма вводится вручную (для пачки — отдельное поле на каждый наряд), по умолчанию подставляется из `customer_payment_amount` наряда;
- админ/superadmin может отметить **один** наряд или пачку неоплаченных через экран «Оплаты заказчиков» (§6.12);
- суммы в списках и сводках **показываются** (колонка «Сумма оплаты», не сумма услуг технику);
- каждый факт оплаты/снятия через подтверждение пишется в журнал (§4.10).

### 4.7. WorkOrderService (строка услуги в наряде)

- `id`, `work_order_id`
- `service_id`
- `assignee_id` — User, **ровно один** исполнитель; должен иметь услугу в своём пуле на момент назначения (проверка при сохранении)
- `quantity` — integer ≥ 1 (по умолчанию 1); единица = единица услуги (например 2 коронки → quantity 2)
- `status` — см. §5
- `technician_price_snapshot` — decimal: копия ставки услуги на момент добавления в наряд (чтобы прайс справочника не менял уже назначенное)
- `started_at`, `completed_at` — nullable
- **Выплата исполнителю (факт, P7):**
  - `technician_paid` — boolean, по умолчанию `false` (UI: «Выплачено» / «Не выплачено», цвета §6.11)
  - `technician_paid_at` — datetime, nullable
  - `technician_paid_by_id` — User, кто поставил/снял последнюю отметку (nullable)
- `notes` — опционально
- timestamps
- фото: Active Storage attachments (0..N), опционально

Сумма к начислению технику по строке: `quantity * technician_price_snapshot`. Учитывается в отчёте ЗП (**начислено**), когда `status == completed`.

Признак `technician_paid` **не** зависит от `completed`: выплату можно фиксировать при любом статусе строки **кроме** случая, когда наряд в `draft` или нет `assignee_id` (§5.4). Частичная выплата суммы строки **запрещена** (только целиком да/нет).

Смена `assignee_id` после выхода из `assigned` — **запрещена** в MVP (post-MVP).

**Удаление / снятие строки из наряда** (admin/superadmin; employee не может):

- **Hard delete** — только если `status == assigned` и `technician_paid == false` (черновой мусор): строка уничтожается.
- **Soft-remove** (`removed_at`, опционально `removed_by_id`) — для `in_progress` / `completed` и/или при `technician_paid == true`: строка исчезает из **активного** состава наряда (show, публичная страница, правила ready/closed), но **остаётся в БД**. Журнал `PaymentEvent`, отчёт ЗП (§7.2) и вкладка начислений в ЛК **сохраняют** факт. Вкладка «Задачи» ЛК снятые строки не показывает.
- Восстановление снятой строки и физический purge в этой версии не делаем. Soft-remove **не** снимает выплату автоматически.

### 4.8. Вложения (фото)

- Active Storage, сервис **Disk**
- Корень хранения — конфигурируемый путь (volume в Docker / локальная папка); **без S3 и без внешних object storage**
- Привязка: к `WorkOrder` (общие фото наряда) и/или к `WorkOrderService` (фиксация исполнения)
- Фото при переводе услуги в `completed` — **опционально**
- **Лимиты MVP:**
  - форматы: JPEG, PNG, WebP;
  - размер файла ≤ **10 MB**;
  - ≤ **20** файлов на наряд (`WorkOrder`);
  - ≤ **10** файлов на строку услуги (`WorkOrderService`).

### 4.9. Зубная формула (odontogram)

Мотивация UX/модели — профессиональные ЗТЛ-программы, в частности [exocad DentalDB](https://wiki.exocad.com/wiki/index.php/DentalDB_Application): клик по зубу на дуге → тип работы, цветовая легенда, нумерация FDI. Полный CAD/CAM exocad **не** копируется (§2).

Нумерация: **FDI** (11–18, 21–28, 31–38, 41–48). Другие системы (Universal 1–32, Palmer) в MVP не поддерживаются.

Хранение в `WorkOrder.dental_formula` (JSONB):

```json
{
  "notation": "fdi",
  "shade": "A2",
  "teeth": [
    { "n": 14, "type": "crown", "material": "zirconia", "shade": null },
    { "n": 15, "type": "bridge", "material": "zirconia", "shade": null },
    { "n": 16, "type": "crown", "material": "cocr", "shade": null }
  ],
  "connectors": [[14, 15], [15, 16]]
}
```

Поля:

- `notation` — всегда `"fdi"` в MVP;
- `shade` — **общий цвет наряда**, код из `config/odontogram.yml` → `shades` (или `null`); свободный текст **запрещён**; синхронизируется с `WorkOrder.tooth_color`;
- `teeth[]` — задействованные зубы; `n` — FDI; `type` — код типа из `config/odontogram.yml` **или `null`**, если зуб только выбран, а параметры ещё не заданы; `material` — код материала **этого** зуба из того же файла (или `null`); свободный текст **запрещён**; `shade` на зубе не используется (всегда null);
- `connectors` — пары соседних зубов `[a, b]` (минимальный аналог DentalDB connector toggles). Графические мосты/кламмеры — вне MVP.

**Типы, материалы и цвета:** единый конфиг `config/odontogram.yml`:
- `types[]` — `code`, `name`, `color`. MVP-набор (9): `antagonist` (Антагонист), `healthy` (Здоровый зуб), `crown` (Коронка), `coping` (Каркас), `veneer` (Винир), `inlay` (Вкладка), `abutment` (Абатмент), `missing` (Отсутствует), `bridge` (Мост);
- `materials[]` — `code`, `name` (выпадающий список в UI). MVP-набор (7): `zirconia` (Zr), `emax` (E.max), `cocr` (CoCr), `titanium` (Ti), `pmma` (PMMA), `pfm` (Металлокерамика), `precious` (Драгоценный сплав);
- `shades[]` — `code`, `name` (Vita Classical и т.п.; выпадающий список «Цвет зубов»).

Меняется правкой файла + рестарт приложения; **без** admin CRUD и без таблиц в БД. Неизвестный `type` отбрасывает зуб; неизвестный `material` обнуляется (зуб остаётся); неизвестный `shade` обнуляется. Старые коды типов из ранних версий конфига при чтении мапятся на новые (напр. `pontic` → `bridge`, `inlay_onlay` → `inlay`).

**UI (Stimulus, вдохновлено DentalDB tooth bow):**
- визуальная **зубная дуга** (SVG): верхняя/нижняя челюсть, FDI, метки R/L (без текстовых подписей «середина/верхняя/нижняя»); заливка зуба цветом типа (style «colorful»);
- обычный клик по новому зубу — выбирает его с `type: null`, `material: null`;
- тип и материал задаются select’ами сверху для **активного** зуба; общий shade — select из конфига;
- `Ctrl`+клик (или `Cmd`+клик) — копирует параметры с активного / последнего зуба с параметрами;
- **connectors** между соседними выбранными зубами (точка/линия; по умолчанию выкл./серый; клик включает зелёный); автопроставление не делается;
- без типа — жёлтая заливка; активный обведён; легенда типов;
- список снизу — **только информирование** (номера зубов, тип, материал); зубы с одинаковым типом и материалом группируются (диапазоны: `12–13`, `31–38, 41–48`);
- на карточке наряда (show) — двухколоночный layout: слева данные/услуги/фото, справа read-only odontogram (sticky на широком экране); на мобилке формула выше основного контента;
- поле `notes` в UI подписано «Описание» и отображается на show;
- ширина контента: общий контейнер `.app-shell` (до ~1600px) для шапки и main;
- пациента можно создать по ФИО прямо в форме наряда **только вместе с врачом** (иначе ошибка).

### 4.10. PaymentEvent (журнал фактов оплаты) — P7

Append-only лог. **Не** касса и **не** банковские транзакции: люди переводят деньги вне системы; в DLM только фиксация факта.

Поля (минимум):

- `id`
- `event_type` — одно из:
  - `technician_paid` / `technician_unpaid` — выплата исполнителю по строке услуги;
  - `customer_paid` / `customer_unpaid` — оплата заказчиком по наряду;
- `actor_id` — User, кто подтвердил действие;
- `work_order_id` — nullable (обязателен для customer_*);
- `work_order_service_id` — nullable (обязателен для technician_*);
- `amount` — decimal, сумма на момент события (для строки: `qty * snapshot`; для наряда: зафиксированный `customer_paid_amount`);
- `note` — опционально;
- `created_at` (событие не редактируется и не удаляется в UI).

Правило пачки: в UI одно подтверждение на набор строк/нарядов; в журнале — **отдельная запись на каждый** объект.

## 5. Статусы и правила переходов

### 5.1. Статусы наряда (`WorkOrder.status`)

Порядок вперёд:

`draft` (черновик) → `in_progress` (в работе) → `ready` (готов) → `sent` (отправлен) → `closed` (закрыт)

Правила вперёд:

1. Созданный наряд стартует в `draft`.
2. Переход `draft` → `in_progress`: вручную admin/superadmin **или** автоматически, когда хотя бы одна услуга переведена в `in_progress`.
3. Переход в `ready`: вручную admin/superadmin; разрешён только если есть **≥ 1** строка услуги и **все** строки в `completed`.
4. Переход `ready` → `sent`: вручную (доставка / выдача заказчику); выставить `sent_at`.
5. Переход `sent` → `closed` (или `ready` → `closed`, если отправка не используется): вручную; ≥ 1 строка услуги; все услуги `completed`; выставить `closed_at`.
6. Закрытый наряд (`closed`): **запрещено** редактировать состав услуг, исполнителей, зубную формулу; разрешён просмотр; `customer_payment_amount` можно править только пока наряд **не оплачен**; факт оплаты — только через подтверждение (§6.9).
7. Удаление наряда: только `superadmin`, и только из `draft`. Soft-hide не требуется в MVP.

Оплата заказчиком **не** является статусом наряда.

### 5.1.1. Откат статусов наряда

Откат **заложен в MVP** для admin/superadmin (кроме выхода из `closed`):

| Из | В | Условия |
|---|---|---|
| `in_progress` | `draft` | нет строк в `in_progress`/`completed` (все `assigned` или строк нет) |
| `ready` | `in_progress` | всегда разрешён admin/superadmin |
| `sent` | `ready` | сбросить `sent_at` в `null` |
| `closed` | * | **запрещено** |

### 5.2. Статусы услуги в наряде (`WorkOrderService.status`)

`assigned` (назначена) → `in_progress` (в работе) → `completed` (выполнена)

Правила вперёд:

1. При создании строки статус = `assigned`; исполнитель обязателен.
2. `assigned` → `in_progress`: исполнитель этой строки, либо admin/superadmin. Писать `started_at`.
3. `in_progress` → `completed`: исполнитель этой строки, либо admin/superadmin. Писать `completed_at`. Фото — опционально.
4. Смена `assignee_id` разрешена только в `assigned` (admin/superadmin).
5. Наряд нельзя перевести в `ready` / `sent` / `closed`, пока есть строки не в `completed` или строк нет.

### 5.2.1. Откат статусов услуги

Только admin/superadmin:

| Из | В | Эффект |
|---|---|---|
| `completed` | `in_progress` | очистить `completed_at`; строка **перестаёт** учитываться в ЗП |
| `in_progress` | `assigned` | очистить `started_at` (и `completed_at`, если был) |

Откат `completed` → `assigned` за один шаг **не** требуется (достаточно двух шагов).

### 5.3. Начисление ЗП

- Момент включения в «заработано» (**начислено**): статус строки `completed`.
- База отчёта §7.2: сумма `quantity * technician_price_snapshot` по строкам с `status=completed` и `completed_at` в выбранном периоде.
- Закрытие наряда **не** требуется для начисления ЗП (отличие от ZTL).
- Признак `technician_paid` — отдельный контур (**выплачено**), см. §5.4; не смешивать с «начислено».

### 5.4. Выплаты исполнителям и оплата заказчиком (P7)

#### 5.4.1. Выплата по строке услуги

Разрешено отметить «Выплачено» / снять отметку, если:

1. у строки есть `assignee_id`;
2. наряд **не** в статусе `draft`;
3. статус строки любой из `assigned` | `in_progress` | `completed`.

Кто:

- исполнитель строки — только свои строки;
- admin — любые строки (в т.ч. выбор исполнителя и пачка его невыплаченных);
- superadmin — как admin + override лимита 30 дней.

Частичная выплата суммы строки **запрещена**.

**Лимит 30 дней:** если `technician_paid == true` и с `technician_paid_at` прошло **более 30 суток**, сменить статус выплаты (снять или снова поставить после снятия в этом окне — имеется в виду любое изменение флага) **нельзя** для `employee` и `admin`. `superadmin` **может** изменить с обязательной записью в журнал.

Каждое изменение → `PaymentEvent` (`technician_paid` / `technician_unpaid`) с `actor_id`.

#### 5.4.2. Оплата заказчиком по наряду

- Только наряд **целиком**: `customer_paid_amount = 0` (не оплачен) или `> 0` (оплачен); частичных сумм нет.
- Кто: admin / superadmin.
- Сумма к оплате: admin задаёт `customer_payment_amount` в форме редактирования наряда; это **не** сумма `quantity × technician_price_snapshot` по строкам.
- Отметить оплаченным / снять оплату: один наряд с карточки **или** пачка через «Оплаты заказчиков» → подтверждение §6.9.
- На подтверждении: сумма **обязательна** и вводится вручную (предзаполнение из `customer_payment_amount`); для нескольких нарядов — поле суммы на каждый отмеченный наряд.
- Суммы отображаются в списках; дата на подтверждении по умолчанию — сегодня (можно изменить до подтверждения).
- Каждое изменение факта через подтверждение → `PaymentEvent` (`customer_paid` / `customer_unpaid`).

#### 5.4.3. Подтверждение (анти-misclick)

Любая массовая или одиночная установка/снятие оплаты (исполнителю или заказчику) идёт через **отдельную страницу подтверждения** (§6.9): сводка объектов, суммы, даты → явное «Подтвердить». Без подтверждения статус не меняется.

## 6. Экраны / user flows

UI: русский язык. Классический Rails (server-rendered views + Hotwire/Turbo/Stimulus по необходимости).

### 6.1. Аутентификация

- Вход по **email** + пароль (Devise).
- Неавторизованный доступ ко всем экранам кроме публичного наряда — редирект на login.
- Отключённый пользователь (`active=false`) не входит.

### 6.2. Личный кабинет сотрудника

- Экран `/my_tasks`: вкладки «Задачи» и «Начисления и оплаты» (единый фильтр дат); `/my_earnings` — редирект на вкладку «Начисления»; список своих строк услуг; фильтры по статусу исполнения (`assigned` / `in_progress` / `completed`), периоду и **выплате** (`technician_paid` да/нет) — P7.
- Карточка строки (`/my_tasks/:id`): данные наряда (номер, пациент, срок, описание), **та же SVG зубная формула read-only**, что на карточке наряда (§4.9), услуга, количество, своя сумма строки, бейдж выплаты (§6.11), действия «Взять в работу» / «Выполнено», действие «Я получил оплату» / снятие (по §5.4), фото строки (клик — просмотр, отдельно скачать/удалить).
- На индексе — сумма выполненных за текущий фильтр (начислено) и при P7 — суммы/счётчики по выплачено/не выплачено; чужие назначения и лабораторные отчёты — нельзя.
- P7: доступ к своему журналу оплат (§6.10) и отчёту по своим услугам/выплатам (§7.7).
- Навигация: «Мои задачи» и «Журналы» для employee; admin/superadmin с `/my_tasks` и `/my_earnings` редиректятся на рабочие экраны.

### 6.3. Список нарядов (admin / superadmin)

- Таблица с фильтрами: статус, заказчик, **поиск по пациенту (фамилия / ФИО, подстрока)**, оплата заказчиком (да/нет). Период и исполнитель — по мере появления в UI (спека допускает).
- **Пагинация:** по **40** записей на страницу (общая для списков лаборатории).
- Каждая строка ведёт на карточку наряда: ссылки на номер, ФИО пациента и действие «Открыть».
- Подсветка просроченного `due_at` (рекомендуется).
- Действия: создать, открыть, сменить статус вперёд/назад (по правилам §5).

### 6.4. Карточка наряда (admin / superadmin)

- Шапка: номер, статусы, заказчик, врач (опционально), пациент (опционально), срок, **описание** (`notes`), цвет зубов (shade).
- Редактор odontogram (§4.9): SVG зубные дуги (DentalDB-like), общий shade из конфига, типы/материалы (select), connectors, легенда; на show и в ЛК техника — общий partial read-only chart.
- Список услуг: добавить из справочника, quantity, назначить исполнителя из пользователей, у которых услуга в пуле; статусы строк; откат статусов строк (admin/superadmin). Удаление: hard delete для `assigned` без выплаты; иначе soft-remove с сохранением истории (§4.7).
- Блок оплаты заказчиком: бейдж «Оплачен заказчиком» / «Не оплачен» (§6.11); для неоплаченного — отображение «к оплате» из `customer_payment_amount`; для оплаченного — `customer_paid_amount` и дата. **Отметить оплату / снять** — только через подтверждение (§6.9). Редактирование `customer_payment_amount` — в форме «Изменить» наряд.
- P7: по строкам услуг — бейджи «Выплачено» / «Не выплачено»; действия выплаты admin (в т.ч. переход к оплате выбранного исполнителя).
- QR-код и копирование публичной ссылки (на основе `public_token`) — §6.7.
- База публичного URL: `PUBLIC_BASE_URL` (ENV) или хост текущего запроса.
- Фото наряда (с лимитами §4.8): клик по миниатюре — lightbox-просмотр; «Скачать» и «Удалить» — отдельные действия.
- **Печать:** кнопка «Печать» → браузерный диалог; лист A4: мета слева от QR, описание под ними, формула и услуги ниже; фото и денежные колонки строк при печати скрываются.

### 6.5. Справочники (admin / superadmin)

CRUD: заказчики, врачи, пациенты, услуги.  
У пациента обязателен врач; у врача заказчик опционален.  
Карточки (show): у пациента — врач/клиника и связанные наряды; у врача — пациенты и наряды; у заказчика — врачи, наряды с суммой оплаты и статусом. Заказчик без врачей/пациентов допустим.  
**Услуги:** список с «Открыть» → карточка show; удаление — только с карточки (не из списка), **запрещено** если услуга есть в строках нарядов.  
**Списки и вложенные таблицы на show:** первая колонка — ссылка на запись (`record_link`); последняя — кнопка «Открыть» (`open_record_link`). На index справочников «Изменить» не дублировать — только «Открыть».  
**Пагинация списков:** по **40** на страницу (наряды, справочники, задачи, оплаты, журналы, отчёты-списки — где применимо).  
Сотрудники: создание/редактирование, роль (роль `superadmin` назначает только `superadmin`), active; пул услуг — multiple select на карточке `/users/:id` (не отдельный раздел).

### 6.6. Доставка

- Экран/фильтр нарядов в статусе `ready` (ещё не `sent`).
- Массовая или поточечная отметка `sent`.

### 6.7. Публичная страница наряда

- URL: `/o/:public_token`.
- Без логина, только GET/read.
- Показывать **всё содержимое карточки для чтения**, включая: номер, статус, срок, заказчик, врач, пациент, описание, зубную формулу (read-only odontogram SVG), список услуг со статусами, именами исполнителей, ставками snapshot и суммами строк, оплату заказчиком (`customer_paid_amount`, `customer_paid_at`), фото (просмотр/скачать, без удаления).
- Если пользователь **авторизован** и имеет право смотреть наряд внутри системы (admin/superadmin или employee с назначением на этом наряде) — на публичной странице кнопка/ссылка **«Открыть наряд»** → `/work_orders/:id` (там действия по услугам: в работу / выполнено для admin; для employee — переход к «Моя задача»).
- Если пользователь **не авторизован** — кнопка **«Войти»** → страница входа (публичный просмотр при этом доступен без логина).
- Сотрудник без назначений на этот наряд — без кнопки «Открыть наряд».
- На карточке наряда (admin): QR-код и копирование публичной ссылки.
- Браузерная печать публичной страницы — как на карточке наряда (§6.4): QR, формула, состав без лишнего chrome.
- Ссылка действует, пока запись наряда существует в БД. Отзыв/перевыпуск токена не реализовывать.

### 6.8. Управление пользователями

- **superadmin:** список всех пользователей, карточка (`/users/:id`), создание, смена любой роли, сброс пароля, active, пул услуг.
- **admin:** список и карточка пользователя; создание и редактирование только **сотрудников** (`employee`); роль admin/superadmin назначить нельзя. На карточке — пул услуг и таблица назначенных услуг по нарядам (статус, оплата, ссылки в наряд).

### 6.9. Подтверждение оплаты (P7)

Отдельная страница (не модал как обязательный UX):

- вход: выбор одной или нескольких строк услуг **или** одного/нескольких нарядов заказчика;
- сводка: что оплачивается/снимается, суммы, исполнитель или заказчик, дата (по умолчанию сегодня, редактируема до подтверждения);
- кнопки «Подтвердить» / «Отмена»;
- после подтверждения — запись `PaymentEvent` на **каждый** объект и редирект обратно в контекст (ЛК / наряд / список).

Админский сценарий «оплатить исполнителя»: выбрать исполнителя → список его подходящих невыплаченных строк → подтверждение пачкой.

Админский сценарий «оплатить заказчика»: один наряд с карточки **или** выбор нарядов на экране «Оплаты заказчиков» → подтверждение с ручным вводом суммы (предзаполнение из `customer_payment_amount`).

### 6.12. Экраны оплат admin (P7, UI)

- **`/technician_payouts`** — список невыплаченных строк услуг (фильтры: исполнитель, статус наряда); галочки → подтверждение выплаты; ссылка на **`/payment_events`** (журнал выплат).
- **`/customer_payment_orders`** — список нарядов и статус оплаты заказчиком (фильтры: заказчик, оплачен/нет, статус); колонка «Сумма оплаты»; галочки → подтверждение; ссылка на **`/customer_payment_events`** (журнал оплат заказчиков).
- **`/payment_events`** — журнал **выплат исполнителям** (§6.10); только `technician_*`.
- **`/customer_payment_events`** — журнал **оплат заказчиком**; только `customer_*`; только admin/superadmin.
- Employee: **`/my_tasks`** (вкладки «Задачи» и «Начисления и оплаты»; **`/my_earnings`** → редирект сюда с `tab=earnings`); **`/payment_events`** — только свои `technician_*`. Наряд на show — read-only для employee, если есть его назначенные услуги.

Навигация в шапке admin: «Оплаты сотрудникам», «Оплаты заказчиков», «Журналы» (→ `/payment_events`, внутри вкладки «Журнал выплат сотрудникам» / «Журнал оплат заказчиков»); employee: «Мои задачи», «Журналы». Отдельной вкладки «Пул услуг» нет: пул задаётся на карточке сотрудника `/users/:id` (admin/superadmin).

### 6.10. Журналы оплат (P7)

Два отдельных read-only журнала (append-only), **не смешивать** выплаты исполнителям и оплаты заказчиком:

**Журнал выплат исполнителям** (`/payment_events`):

- Admin/superadmin: все `technician_*`; фильтры: период, исполнитель, тип.
- Employee: только свои строки (`technician_*`).

**Журнал оплат заказчиков** (`/customer_payment_events`):

- Admin/superadmin: все `customer_*`; фильтры: период, заказчик, тип.
- Employee: **нет доступа**.

### 6.11. Цвета статусов оплаты (P7)

- «Выплачено» / «Оплачен заказчиком» — **зелёный** бейдж.
- «Не выплачено» / «Не оплачен» — **красный** бейдж.
- Единый стиль в списках, карточке наряда, ЛК и отчётах.

## 7. Отчёты

### 7.1. Наряды за период

Доступ: `admin`, `superadmin`.

- Фильтр по дате создания (`created_at`); дополнительно: статус, заказчик, оплата заказчиком (да/нет); UI: `/reports/work_orders`.
- Колонки: номер, даты, заказчик, пациент, статус, срок, признак оплаты заказчиком (бейдж §6.11).
- Экспорт CSV с теми же фильтрами: UTF-8 **с BOM**, разделитель `;`, CRLF (корректное открытие кириллицы в Excel на Windows). Генерация через `SimpleCsv` (без гема `csv` Ruby 3.4).

### 7.2. Оплата труда техников (начислено)

Доступ: `admin`, `superadmin`.

- UI: `/reports/payroll`.
- Период по `completed_at` строк услуг.
- Фильтры: сотрудник, выплачено/не выплачено, услуга.
- Группировка по сотруднику: сумма **начислений**, количество единиц.
- Детализация: наряд, услуга, qty, ставка snapshot, сумма, дата выполнения; колонка/фильтр **выплачено** (`technician_paid`).
- Учитывать в «начислено» только `status = completed`; откат `completed` убирает строку из начислений. Снятые с наряда (`removed_at`) выполненные строки **остаются** в начислениях.

### 7.3. Неоплаченные заказчиком наряды

Доступ: `admin`, `superadmin`.

- UI: `/reports/unpaid` (ссылка на «Оплаты заказчиков»).
- Наряды с `customer_paid_amount = 0`; фильтры: статус, период создания, заказчик, только с `customer_payment_amount > 0`.
- Колонки: номер, заказчик, даты, статус, срок; **сумма оплаты** (`customer_payment_amount`), где задана; «Открыть» на наряд.

### 7.4. Воронка и задачи на руках

Доступ: `admin`, `superadmin`. UI: `/reports/funnel`.

- Счётчики нарядов по всем статусам (снимок «сейчас»).
- Активные строки услуг в `assigned` / `in_progress` (без soft-remove), сгруппированные по исполнителю.

### 7.5. По заказчикам за период

Доступ: `admin`, `superadmin`. UI: `/reports/customers`.

- Период по дате создания наряда.
- По каждому заказчику: число нарядов, сумма уже оплаченная (`customer_paid_amount`), долг (сумма `customer_payment_amount` по неоплаченным).

### 7.6. По услугам за период

Доступ: `admin`, `superadmin`. UI: `/reports/services`.

- Период по `completed_at` выполненных строк; те же правила начисления, что §7.2 (включая soft-removed completed).
- По каждой услуге: сумма количества и сумма начислений.

Хабы лабораторных отчётов: `/reports` (admin/superadmin). Employee — отказ к §7.1–7.6.

### 7.7. Отчёт исполнителя по услугам и выплатам (P7)

Доступ: `employee` (только свои данные); `admin`/`superadmin` могут смотреть тот же UI для себя или (для admin) выбрать исполнителя — по решению реализации, минимум: employee видит **себя**.

- Период; фильтр выплачено / не выплачено / все.
- Строки: наряд, услуга, qty, сумма, статус исполнения, бейдж выплаты, даты.
- Итоги: сумма начислений (completed) и/или сумма в выборке по фильтру выплаты — ясно подписать в UI.

## 9. Нефункциональные требования

1. Целевой запуск для клиента: `docker compose up` на Windows (Docker Desktop) и на Unix.
2. Пути файлов Active Storage — через ENV (`ACTIVE_STORAGE_ROOT` / `HOST_STORAGE_PATH`), не hardcoded Unix-only абсолютный путь без настройки.
3. Часовой пояс и локаль по умолчанию: `ru`, валюта отображения ₽ (внутренние экраны и публичная страница — суммы можно показывать).
4. Публичный `public_token` — криптостойкая случайная строка (достаточная длина, не sequential id).
5. Пароли не хранить в открытом виде (Devise).
6. Объём: малая лаборатория, небольшой трафик и немного фото — оптимизация «на миллионы» не нужна.
7. Один инстанс = одна лаборатория.
8. Seed: как минимум один `superadmin`; для development допускается объёмный демо-сид (отключается `SKIP_DEMO_SEED=1`).
9. HTTPS: опционально включаемый через ENV/proxy; по умолчанию HTTP для LAN ок.
10. **Тесты сценариев:** основные пользовательские потоки каждой фазы разработки MUST покрываться автоматизированными **system** (предпочтительно, Capybara e2e) и/или **integration** тестами Rails. Unit/model — дополнение, не замена. Фаза не принимается без зелёного `bin/rails test` по её сценариям (см. `docs/AGENT_PLAN.md`).
11. Списки с потенциально большим числом записей пагинируются (**40** на страницу).

## 10. Критерии приёмки MVP

MVP принят, если выполнено всё ниже:

1. Пользователи трёх ролей входят в систему; права из §3 соблюдаются (в т.ч. employee не создаёт наряды). Seed создаёт `superadmin`. Сценарии входа и прав подтверждены system/integration тестами.
2. CRUD справочников: заказчик, врач, пациент, услуга; у услуги задаётся `technician_price`.
3. Админ задаёт сотруднику пул услуг; нельзя назначить на строку наряда исполнителя вне пула.
4. Админ создаёт наряд с заказчиком; пациент и врач **опциональны**; срок, odontogram (§4.9), список услуг (0..N, для `ready+` — ≥1) с одним исполнителем на строку. Пациент в справочнике всегда с врачом; inline-пациент на форме наряда — только при указанном враче.
5. Исполнитель в ЛК видит свои услуги, переводит `assigned → in_progress → completed`, может прикрепить фото в лимитах §4.8.
6. Нельзя закрыть/пометить готовым наряд с невыполненными услугами или без строк услуг.
7. ЗП-отчёт считает суммы по `completed` за период по snapshot-ставкам; откат `completed` убирает строку из начислений.
8. На наряде задаётся сумма к оплате заказчиком (`customer_payment_amount`); факт оплаты — через подтверждение; отчёт «неоплаченные» и экран «Оплаты заказчиков» работают.
9. Статус `sent` доступен для готовых нарядов (сценарий доставки); откаты статусов наряда работают по §5.1.1.
10. QR/ссылка открывает публичную страницу без логина; на странице видно полное содержимое включая деньги; страница работает, пока наряд в БД.
11. Фото сохраняются на диск через Active Storage (каталог хоста / `HOST_STORAGE_PATH`) и отдаются приложением; `docker compose up` поднимает стек на Windows/Unix.
12. Отчёт «наряды за период» доступен admin/superadmin; также доступны начисления, долги, воронка, сводки по заказчикам и услугам (§7).

## 10.1. Критерии приёмки P7 (оплаты и журнал)

P7 принят, если:

1. Исполнитель в ЛК видит свои строки с фильтром выплачено/не выплачено и бейджами (§6.11).
2. Исполнитель может через страницу подтверждения отметить «Я получил оплату» / снять отметку по своим строкам при правилах §5.4; админ — по любому исполнителю (в т.ч. пачкой).
3. Через 30+ суток после `technician_paid_at` employee и admin **не** меняют выплату; superadmin может (с записью в журнал).
4. Админ фиксирует оплату заказчиком по одному наряду или пачке через «Оплаты заказчиков» — только целиком, через подтверждение с **ручным** вводом суммы (не из суммы услуг); суммы видны в списках.
5. Частичных оплат нет ни по строке услуги, ни по наряду.
6. Журнал `PaymentEvent` append-only: admin видит всё с фильтрами; исполнитель — только свои `technician_*`.
7. Отчёт §7.7 доступен исполнителю по своим данным.
8. Сценарии выше покрыты system/integration тестами.

## 11. Явные «не делать в v1»

Повторение для агента — **не реализовывать**, даже если есть в `ZTLHelp.pdf` или exocad:

- работы (customer billable items), скидки/НДС, счета и акты PDF как обязательный модуль;
- платежи с оприходованием на несколько нарядов, возвраты, баланс заказчика, касса/банк (в DLM только **факты** оплаты, §4.10 / §5.4);
- склад и материалы;
- категории оплаты техника 1/2/3;
- откат из `closed`;
- перевыпуск/отзыв QR;
- графическая формула с мостами/кламмерами как отдельная CAD-отрисовка (connectors в JSON — ок);
- кабинет клиники / врача;
- хранение файлов в BYTEA PostgreSQL или в S3;
- CAD-материалы, milling, implant libraries DentalDB.

## Приложение A. Глоссарий

| Термин | Значение в DLM |
|---|---|
| Наряд (WorkOrder) | Заказ-наряд лаборатории; ≤1 пациент (опционально) |
| Услуга (Service) | Операция техника; имеет ставку ЗП |
| Строка услуги | Конкретная услуга в наряде с исполнителем и статусом |
| Пул услуг | Набор услуг, которые сотрудник имеет право выполнять |
| Оплата заказчиком | Плановая сумма `customer_payment_amount` + факт `customer_paid_*` на наряде целиком; не касса |
| Выплата исполнителю | Факт на строке услуги (`technician_paid`); не банковская транзакция |
| Начислено | Сумма по `completed` × snapshot (ЗП-отчёт) |
| Выплачено | Отметка `technician_paid` (может быть до/после completed при правилах §5.4) |
| PaymentEvent | Append-only журнал фактов оплаты |
| Публичная ссылка | Read-only URL по `public_token` |
| Odontogram | JSONB зубная формула FDI + типы работ (DentalDB-inspired) |

## Приложение B. Связь с ZTL

`ZTLHelp.pdf` — справочник поведения исходной десктопной системы AverSoft ЗТЛ. Использовать только для уточнения доменных терминов (наряд, заказчик, доставка, операция). Любое расхождение с §§1–11 этой спецификации разрешать в пользу DLM MVP.
